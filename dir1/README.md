이 문제는 네비게이션/경로 탐색 시스템에서 다익스트라 알고리즘의 DB 쿼리 최적화에 관한 것입니다. 핵심을 정리해드리겠습니다.

## 문제 분석

**기존 방식의 문제점**: 다익스트라 알고리즘에서 각 간선(edge)의 가중치를 구할 때마다 개별 DB 쿼리를 날리고 있었다는 것입니다.

## 가중치 종류별 분석

다익스트라에 필요한 가중치는 3가지 기준입니다:

1. **거리** — 정적 데이터 (변하지 않음)
2. **최고 제한 속도** — 정적 데이터 (변하지 않음)
3. **평균 이동 시간** — 동적 데이터 (시간대별로 달라짐)

## 최적화 방법

### 거리 & 최고 제한 속도 → 1회 쿼리

이 두 값은 시간에 따라 변하지 않으므로, 모든 구간의 거리와 제한 속도를 **한 번의 쿼리로 전부 가져올 수 있습니다**.

```sql
-- 기존: 구간마다 개별 쿼리 (N회)
SELECT distance, speed_limit FROM edges WHERE edge_id = ?;

-- 최적화: 전체를 한 번에 조회 (1회)
SELECT edge_id, distance, speed_limit FROM edges;
```

가져온 데이터를 메모리에 Map/Dictionary로 캐싱해두고 알고리즘 내에서 참조합니다.

### 평균 이동 시간 → 최대 3회 쿼리 (1시간 이내 경로)

평균 이동 시간은 **시간대(time slot)에 따라 달라지는 동적 데이터**입니다. 핵심 아이디어는:

- 출발 시각이 속한 시간대의 데이터를 먼저 1회 쿼리로 전체 구간을 가져옴
- 경로를 탐색하다가 다음 시간대로 넘어가면 해당 시간대 데이터를 추가 쿼리
- 1시간 이내 경로라면, 최대 3개 시간대에 걸칠 수 있음 (예: 30분 단위 슬롯이라면 8:20 출발 → 8:00대, 8:30대, 9:00대)

```sql
-- 시간대별로 모든 구간의 평균 이동 시간을 한 번에 조회
SELECT edge_id, avg_travel_time 
FROM edge_travel_times 
WHERE time_slot = ?;
```

탐색 중 새 시간대에 진입할 때만 추가 쿼리를 수행합니다.

## 기존 vs 최적화 비교

| | 기존 | 최적화 |
|---|---|---|
| 거리/속도 | 간선 수 × 2회 (수십~수백 회) | **1회** |
| 평균 이동시간 | 간선 탐색마다 1회 (수십~수백 회) | **최대 3회** |
| **합계** | O(E) 회 | **최대 4회** |

## 추가 최적화 포인트

- **인덱스 최적화**: `time_slot` 컬럼에 인덱스 설정
- **커넥션 풀링**: DB 커넥션 재사용
- **캐싱**: 자주 조회되는 시간대 데이터를 Redis 등에 캐싱
- **Batch/Bulk 조회**: `WHERE IN` 절 활용

핵심은 **"구간별로 쿼리하지 말고, 조건별로 모든 구간을 한 번에 가져와라"**는 것입니다.
